# Rostrum3D engine contract — the scene description

*Team Hem, brief H12, 2026-10-21. Version **1.30** (§ 5). Between the Python layer (`apps/3d/python/rostrum3d/`) and the C++ core (`apps/3d/core/`, program `rostrum3d-core`).*

## 0. The document and USD: who owns what

**The Rostrum document (`.trd`, on `rostrum_core`) is the single source of truth. USD is what it compiles to.**

```
person (GUI) ─┐                                   ┌─ Storm   (viewport, fast)
agent (MCP) ──┼─ operations ─ document (.trd) ─ compile ─ scene JSON ─ rostrum3d-core ─ USD stage ─ Hydra ┼─ Cycles  (final)
script ───────┘   one history, merge on re-run          (this file)      (C++)        (in memory)      └─ Rostrum stylized
                                                                                         └─ save → .usda (hand-off)
```

- **Every change is an operation on the document** (OPERATIONS.md): one history, undo per author, script re-runs merge and never wipe what a person moved. USD never holds a value the document doesn't. So there is no second place an edit can live and get lost.
- **The core builds the stage from the scene description**, every time it is sent: one anonymous root layer, prims at `/World/<id>/<child id>…`. Item ids are prim names, so a prim path always leads back to its item (that is how "what's here" answers with an item id).
- **Imported USD stays a file.** An `import` item *references* the file (a USD reference arc); the file is never rewritten. A person's or agent's changes to an imported thing (move it, give a part another material, hide a part) are document values, compiled to **overrides in our layer**, which is stronger than the referenced file. Re-importing a newer version of the file keeps those overrides.
- **Why not make USD the source of truth?** USD layers have no notion of who changed what, no per-author undo, no three-way merge for script re-runs, no `valid_when`. Those live in `rostrum_core` and are shared with 2D, Sound and the Editor. Editing the USD stage directly would be a side door around them (AGENTS.md rules 3 and 4). USD stays what it is best at: the scene graph every renderer and every other 3D program reads.
- **Animation is the one key model** (the 2D keys: `t`, `v` or `c`, `ease`, same easing table). The Python layer evaluates the keys and **bakes every frame** of the shot into the scene description; the core writes them as USD time samples. One evaluator, no second easing table in C++, and a saved `.usda` plays the same in any USD program.

## 1. The conversation (`rostrum3d-core serve`, one JSON object per line each way)

One long-lived process. Each request is one line `{"<request>": {…}}`; each reply is one line. Errors are `{"ok": false, "error": "…"}` naming the request, the item id and the field; **the process keeps serving**. Unknown request names, renderer names, camera ids, view names or fields are errors listing what is accepted. Nothing is ever guessed.

(v1.17) While a preview stroke's pointer moves and the clay keeps up, the clay's catch-up runs on 1 thread below normal priority (`ROSTRUM3D_CLAY_CATCHUP_MOVING_THREADS`, 0 = always wide); it goes wide when its waiting dabs exceed 10 ms at the wide pace, after 40 ms with no dab, and at `end`; live = replay unchanged. ## 2. The scene

```json
{
  "format": "rostrum-3d-scene", "version": 1,
  "shot": {"id": "hero", "fps": 24, "start": 0, "end": 47, "shutter": 0.5},
  "world": {"background": [0.0, 0.0, 0.0], "environment": null},
  "materials": [
    {"id": "mat_glass", "props": {"baseColor": [0.97, 0.99, 0.98], "metallic": 0, "roughness": 0, "transmission": 1, "ior": 1.52, "…": "…"}}
  ],
  "items": [
    {"id": "device", "type": "group", "props": {"x": 0, "y": 0, "z": 0, "rx": 0, "ry": -12, "rz": 0, "sx": 1, "sy": 1, "sz": 1, "visible": true},
     "anim": {"ry": [-12.0, -11.9, "… one value per frame, start..end …"]},
     "children": [
       {"id": "body", "type": "mesh", "props": {"…transform…": 0, "shape": "box", "width": 0.074, "height": 0.017, "depth": 0.098, "bevel": 0.004, "segments": 4, "material": "mat_alu"}},
       {"id": "screen", "type": "mesh", "props": {"shape": "box", "…": "…", "material": "mat_glass"}}
     ]},
    {"id": "key", "type": "light", "props": {"…transform…": 0, "kind": "rect", "width": 0.7, "height": 0.45, "color": [1, 1, 1], "intensity": 7, "exposure": 0, "temperature": 5600}},
    {"id": "cam", "type": "camera", "props": {"…transform…": 0, "focalLength": 100, "sensorWidth": 36, "dof": true, "fStop": 4, "focusDistance": 0.38, "near": 0.01, "far": 100}}
  ]
}
```

- **Units:** metres, Y up, angles in degrees, time in frames at `shot.fps` (the core's frame *n* is USD time code *n*). `start`/`end` are inclusive.
- **`shutter`** (v1.7, motion blur): how long the shutter is open, in frames, 0..1 (`0` = no motion blur; the shot's Shutter of 180° is 0.5), centred on each frame. The core writes it as every camera's `shutter:open` = −shutter/2 and `shutter:close` = +shutter/2 (USD's frame-relative shutter) and, for every animated transform, extra time samples at each frame ± shutter/2 (the straight line to the neighbouring frame, what USD reads there anyway): Cycles' Hydra plug-in spreads the samples it finds inside the shutter evenly over it, so they must sit at open, frame and close. A `render` or Final `view` through a camera with an open shutter switches Cycles' `motion_blur` on. The camera's move and every object's move blur (v1.8): the engine also gives Cycles the shutter as the render settings `rostrum:shutterOpen` / `rostrum:shutterClose` (set only from an open shutter, kept while a free camera looks), and our patched Hydra plug-in (`libs/cycles-rostrum.patch`, hydra/geometry.inl) samples each object's transform inside it, as it does the camera's. A mesh that changes its own shape (points moving) is not sampled and stays sharp. Storm (Quick) shows no motion blur.
- **Colours are linear** (scene-referred, Rec.709 primaries) as three floats. The document stores `#rrggbb` (sRGB) for people; the compiler converts.
- **Every field is present** in `props` (the compiler fills in defaults), so the core has no defaults table. The fields, their types and ranges are `rostrum3d/fields.py` (the one table).
- **Transform** (every item): `x y z` (translate), `rx ry rz` (rotate, degrees, applied X then Y then Z, i.e. USD `xformOp:rotateXYZ`), `sx sy sz` (scale), `visible`. Authored as `translate`, `rotateXYZ`, `scale`, in that order. A `mesh` may carry `guide: true` (sent only when on): USD's `guide` purpose, drawn and picked by `view` (Quick and Final) and never by `render`, `look_frame` pictures or paint (a handle to move, like Change near's ball); a combine's input reads and ignores it. Aiming at a point is the compiler's job: it turns an aim into `rx ry rz`, frame by frame when animated.
- **`anim`**: a field listed here is animated. Its list holds one value per frame from `start` to `end` (numbers, or `[r, g, b]` for colours), written as USD time samples. The value in `props` is then ignored.
- **`children`**: items inside a `group` or an `import`; their transforms are relative to the parent. A `combine`'s children are its inputs (below), not items of their own.
- Ids match `[A-Za-z_][A-Za-z0-9_]*` and are unique in the scene (they are prim names).

### Item types

| type | props (besides the transform) | USD |
|---|---|---|
| `group` | — | `Xform` |
| `mesh` | `shape`: `box` (`width height depth bevel segments`), `sphere` (`radius segments`), `cylinder` (`radius height bevel segments`), `cone` (`radius height segments`: base radius, base to point), `capsule` (`radius height segments`: height end to end, at least `2 × radius`, else fails loudly), `plane` (`width depth`), `disc` (`radius segments`), `torus` (`radius tube segments`), `outline` (`outline depth bevel segments` + four face materials, see below); `smooth` (bool: smooth normals, or flat); `material` (id or `""`) | `Mesh` with points, normals and `primvars:st` (UVs, 0..1 per face group, so textures land), centred on its origin, made by the core |
| | **Bones (v1.10, brief 19; core/src/skin.cpp).** A `mesh` node may carry `"skin": {"rest": [[hx, hy, hz, tx, ty, tz] per bone], "pose": [[[m00, m01, m02, m10, m11, m12, m20, m21, m22, tx, ty, tz] per bone] per frame, start..end]}` beside `props`, all in the mesh's own space: each bone's head and tail at rest, and per frame each bone's move from rest (p_now = M·p_rest + t, M row by row). Bones are not prims; the compiler sends only this. The core weights every point automatically (1 / distance⁴ to each rest bone, the 4 nearest, normalised: a joint is shared smoothly over about the mesh's thickness) and bends the points and normals with USD skel's linear blend skinning (`UsdSkelSkinPointsLBS`), written as **time samples on the mesh's points, normals and extent**, so Storm (Quick) and Cycles (Final) draw the same bend. A bent mesh doesn't motion-blur its bend (points moving stay sharp, as above). **Fails loudly:** an empty `rest` or `pose`, a frame without one move per bone, a list that isn't 6 / 12 numbers. |
| `combine` (v1.6) | `op`: `union`, `subtract` or `intersect`; `material` (id or `""`); `children`: 2 or more `mesh` or nested `combine` nodes, the first being the base. `anim` animates the combine's own transform and `visible`, as for a group | One `Mesh` at the combine's path, made by the core with Manifold (core/src/boolean.cpp, stage_combine.cpp): triangles, vertex normals, `primvars:st` carried over from the inputs (cut faces keep the cutter's UVs, normals turned to face out) |

### Extruded outlines (v1.3)

Shape `outline`: a flat 2D outline (text, a logo) pushed out into a solid with rounded edges (core/src/extrude.*, outline_offset.*). The Python side turns text, SVG and drawn paths into it; the core only extrudes.

```json
{"shape": "outline", "smooth": true, "depth": 0.01, "bevel": 0.002, "segments": 24,
 "outline": [{"outer": [[0, 0], [0.05, 0], [0.05, 0.07], [0, 0.07]],
              "holes": [[[0.01, 0.01], [0.01, 0.03], [0.04, 0.03], [0.04, 0.01]]]}],
 "material": "mat_gold", "frontMaterial": "", "bevelMaterial": "", "sideMaterial": "mat_dark", "backMaterial": ""}
```

- `outline`: a list of shapes, each one `outer` contour and its `holes` (each a list of `[x, y]`, metres, in the item's XY plane, front facing +Z). Curves arrive already flattened; no repeated closing point. Outers go counter-clockwise and holes clockwise seen from +Z, but the core fixes the direction itself by signed area. Checked loudly: a contour has at least 3 different points (repeats in a row are dropped), finite numbers and some area; the edges of one shape (outer and its holes) never cross. Overlapping parts of one glyph must be merged before they are sent. Separate shapes may overlap (they are separate solids).
- `depth` ≥ 0, along Z, centred: front cap at +depth/2, back cap at −depth/2. `0` = a flat card, front and back faces only.
- `bevel`: a rounded edge (quarter circle) on the front and back. 0 ≤ `bevel` ≤ depth/2. Each cap is the outline moved `bevel` inwards (along each corner's mitred direction, so straight edges stay straight; a needle-sharp corner moves at most 4 × `bevel`); the bevel rounds out to the full outline, and the side wall runs between the two bevels. When the moved outline of a shape would cross itself or turn inside out, the scene fails naming the shape and the largest bevel that works.
- `segments`: steps around each bevel = clamp(`segments`, 1, 16), the same meaning as a box's bevel, capped (the outline's curves are already flattened, so `segments` sets nothing else here).
- `smooth`: side and bevel normals are smooth along curves and split where the outline turns more than 30° (an L has hard corners, an O is smooth); caps are always flat. `smooth: false` = every face flat.
- UVs (`st`): caps 0..1 over the bounding box of the whole outline (the back mirrored, so a texture reads right from behind); side and bevel: u = distance along each contour divided by its length, v = 0 at the back edge to 1 at the front edge.
- **Face materials** `frontMaterial`, `bevelMaterial`, `sideMaterial`, `backMaterial`: a material id or `""`. `""` = the mesh's `material`; for `bevelMaterial`, `""` = the front's material. The mesh gets `GeomSubset`s of faces (family `materialBind`, type `partition`; named `front`, `bevel`, `side`, `back`, an empty one left out), each bound to its material; `material` stays bound on the mesh too. Storm and Cycles both read them.
- **`uvs`** (v1.11, painting): `[]` or one (u, v) per face corner of the built mesh, flat (`[u0, v0, u1, v1, …]`, the `unfold` reply's layout): they become the mesh's `st`. A count that doesn't match the built mesh (its shape changed since it was unfolded) is an error, never stretched.
- Other shapes are sent these fields too (every field is present) and ignore them.

**Blocks (v1.26, Hem brief 23; core/src/material_blocks.*).** `blocks`: `""` or the absolute path of the material's

changed graph is a new path). Read with USD's MaterialX reader (usdMtlx); the document's material must use a nodegraph
`NG_blocks` whose outputs are named after the Surface inputs they feed: `baseColor`, `roughness`, `metallic`,
`emissionColor` (× `emissionStrength`), `normal`. Each node in `NG_blocks` is a Rostrum block (nodedef id
`ND_rostrum_<type>…`: `noise`, `pattern`, `image`, `mix`, `ramp`, `curve`, `colour_adjust`, `bevel`, `occlusion`, from
`core/mtlx/rostrum_blocks.mtlx`, found through `PXR_MTLX_PLUGIN_SEARCH_PATHS`, which the runtime sets). **Cycles:**
each block becomes its own nodes (`noise_texture` on object coordinates; Pattern's checks / stripes / weave as
`math` nodes on the UVs turned by `vector_rotate` and scaled by `vector_math`, only the picked shape; `image_texture`, `mix_color`, `rgb_ramp` /
`float_curve` sampled at 256, `hsv` + `brightness_contrast`, `bevel`, `ambient_occlusion`) wired into the principled
BSDF. **Storm:** `NG_blocks` referenced under `/World/Looks/<id>/Blocks` and an `ND_UsdPreviewSurface_surfaceshader`
(`MtlxSurface`, the Preview's values and pictures as MaterialX images) on `outputs:mtlx:surface`, so Storm's MaterialX
code draws the blocks from their nodedefs' nodegraphs; `normal` is Final only (Bevel shading, Ambient occlusion are
Cycles nodes; their Storm nodegraphs give a flat normal / no darkening). Noise in Storm is MaterialX's fractal noise,
in Cycles Cycles' own: the same scale and detail, not the same pattern. **Fails loudly:** a path that isn't absolute or
doesn't exist; a document without `NG_blocks` in a material; a node that isn't a Rostrum block (named); a wire from an
output a block doesn't have or into an input that takes none; an `NG_blocks` output that isn't a Surface input.
Stylized blocks (Lines, Light to colour, Halftone) are the material's own fields above; the document only carries them
for other programs.

**Stylized blocks (v1.23, Sam brief 22; core/src/material_stylized.*, light_to_color.*).** What each renderer shows: **Storm** only the base colour, image and glow (it ignores all three blocks); **Cycles** shows Light to colour (not Lines or Halftone); **Stylized** shows all three. Every material gets `/World/Looks/<id>/Stylized` (`info:id = "rostrum_stylized"`) on `outputs:rostrum:surface`, inputs all authored as plain values: `baseColor` (color3f; linked to the `PreviewBaseColor` UsdUVTexture's `rgb` when a base colour image is set, the value still authored), `emission` (color3f = `emissionColor` × `emissionStrength`), `opacity` (the UsdPreviewSurface's), `lines` (bool), `linesWidth`, `linesColor` (color3f), `linesTaper`, `linesWobble`, `linesCreaseAngle`, `lightToColor` (bool), `litColor` / `midColor` / `shadowColor` (color3f), `shadowBelow`, `litFrom`, `lightSoftness`, `lightSmooth` (bool: `lightEdges` is `"smooth"`), `halftone` (bool), `halftoneLines` (bool: `halftoneShape` is `"lines"`), `halftoneSize`, `halftoneAngle`, `halftoneColor` (color3f); floats unless named. The stylized renderer asks for the `rostrum` render context; a material without the shader (another USD file) falls back to its UsdPreviewSurface.

**How lit** (one definition for Cycles and Stylized; **DECISION** brightness from the light's real intensity):
`how_lit(P, N) = clamp( Σ_lights Y(c_i)·E_i(P)·max(N·L_i, 0)·vis_i + Σ_domes Y(c_d)·E_d·(0.5 + 0.5·N·up_d), 0, 1 )`.
E_i is what a **white matte surface** facing the light shows (its irradiance / π) in the units every renderer uses (§ Item types, `light`; H19, `tools/light_check.py`), from p = `intensity × 2^exposure`, the colour c_i (× its colour temperature), Y = Rec.709 luminance: distant `p/π` (the light's lux, normalize or not, as both renderers draw it); sphere `p·r²/d²` (normalize: `p/(4π·d²)`); disk `p·r²·cosθ_light/d²` (normalize: `p·cosθ_light/(π·d²)`); rect / strip `p·w·h·cosθ_light/(π·d²)` (normalize: `p·cosθ_light/(π·d²)`); a spot (sphere with a cone) × a smoothstep from the cone's edge in over its softness; dome: its picture × colour × intensity × 2^exposure as a white floor facing the dome's up shows it ((1/π)∫ picture·cos over the upper half, computed once per picture by the core and written on each dome as `primvars:rostrum:domeLevel`, color3f, for the stylized renderer). Sizes scale with the light's transform. vis_i: cast shadow (Cycles: a raycast from P + 1 mm·N towards the light, as long as the distance; Stylized: its shadow maps); a light with `shadows` off has none. So how lit 1 = white paper under the scene's lights looks white at exposure 0. Bands: **steps**: below `shadowBelow` the shadow colour, below `litFrom` the middle one, else the lit one; **smooth**: piecewise linear, shadow → middle over `shadowBelow ± lightSoftness`, middle → lit over `litFrom ± lightSoftness`. `shadowBelow` > `litFrom`: `litFrom` counts for both. Not counted: `lightsOnly` links, a panel's `spread`, bounced light.

**Light to colour in Cycles.** With `lightToColor` on, `outputs:cycles:surface` is a node graph built after the scene's lights (the principled BSDF stays authored, unconnected): per light, the 8 strongest of the scene (by their largest E at 1 m over the shot), `cycles_geometry` → `vector_math` (direction, normalized: `raycast.direction` is a normal socket that Cycles feeds the surface normal when nothing is linked) → `dot_product` with the normal → `math maximum 0` → × `raycast` `1 − is_hit` → × (panels) the cos off the light's axis / (spots) a `map_range` smoothstep → ÷ d² (`dot_product` of the vector to the light with itself) → × E_i's constant; domes `0.5 + 0.5·N·up`; summed (`math add`) → `rgb_ramp` (a 1024-entry table of the bands above; `interpolate` false for steps, true for smooth) → `vector_math multiply` by the base colour (or what feeds the principled `base_color`: the image, decoded) → `vector_math add` the glow (`emissionColor × emissionStrength`, or its image × strength) → `emission` strength 1. Light places, directions and brightness are time samples, one per frame of the shot, when they change. **First use of the raycast node compiles an OptiX kernel once (~3 minutes, ~3 GB RAM: proofs/3d-painterly).**

**A picture per frame** (v1.4): a material may carry `"anim": {"emissionTexture": [one absolute image path per frame, start..end]}`; no other material field can change per frame. The core writes them as **time samples on the texture's file input** (Cycles `filename`, Storm `file`; asset paths are held, never blended), so one stage plays the whole shot like every other animated field. Both renderers read material inputs through UsdImaging, which should mark a time-sampled shader input as varying and re-read it when the frame changes. **Not yet seen working (H22):** the materials turntable video (`tools/materials_turntable.py video`) is the check: its screen shows its own 2D frame number. If the screen stays on one picture, the fallback is to send one scene per frame for shots that use it. Every path is checked (absolute, exists) before anything is built.

The document's `emissionRender` (the id of a 2D item of the project) never reaches the core: the compiler (`material_scene.py`) takes that item's newest finished `pictures` render (`rostrum_core.project.latest_render`), which must be a PNG sequence, and gives each shot frame *f* the 2D file of the same moment: `first + floor((f / fps − frames.start) × fps2)`, held at the first and last file. A still render gives one `emissionTexture`; a sequence gives the `anim` list. Loud: no project folder, no such item, not a 2D item, not rendered, no PNG frames, a frame file missing.

**Storm can't show:** anisotropy and its direction, sheen, coat tint and coat IOR, thin film, bump, `subsurfaceRadius`. **Subsurface in Storm** is a hint: `diffuseColor` leans `0.25 × subsurface` of the way toward `subsurfaceColor` scaled to the base colour's luminance (same brightness, the inside colour's hue); no soft shadows, no glow through thin parts. Rough glass can't blur what is behind it in Storm, so it is drawn less see-through and milkier the rougher it is (`see_through = transmission × (1 − 0.6 × roughness)` sets both the diffuse share and the opacity).

- **USD:** a `PointInstancer` at the item's path with the transform; the `children` are built under it as its `prototypes` (any `mesh`, `combine`, `import`, `group` or `clay`; not a light, camera or copies), so they are drawn only as copies, each copy through its source's own transform. Per copy: `protoIndices`, `positions`, `orientations`, `scales` (uniform), `ids` = the copy's index (0, 1, …).
- **Layouts** (the copies item's own space): `line`: copy i at i × (spacingX, spacingY, spacingZ); `grid`: column (i mod `columns`) × spacingX, row (i div `columns`) × spacingZ, `count` copies in all; `circle`: `count` copies round Y at `radius`, the first on +Z, `faceOut` turns each so the source's +Z points outward; (v1.29) `pour`: `count` copies anywhere in a disc of `radius` round the origin in the item's own XZ plane (evenly by area, from the seed), leaving as a stream when it falls (§ Simulation); `surface`: on the meshes of item `surface` (a `mesh`, `combine` or `import`, as it is at the shot's first frame), area-weighted, each at least `minSpacing` from the ones before it, `count` of them or (`amountBy` density) world area × `density`; when the surface is full at `minSpacing` the rest come closer (the gap × 0.7 by steps, down to touching), so `count` is always met; `alongSurface` stands each on the surface's direction (+Y along the face's normal); `onTop` keeps only the faces whose world normal points up (within 60° of straight up: Y ≥ half its length), so a box gives its top alone. The first copies stay where they are when the count grows.
- **Vary**, from `seed` alone (each copy has its own numbers: the same seed gives the same copies whatever else changes): `varyMove` moves each up to that many metres per axis (on a surface, along it only), `varyTurn` turns each up to ± that many degrees round its own up (Y), `varyScale` sizes each 1 ± up to that share. `varyStart` (seconds, v1.28; a falling copies item only, left out when 0) makes each copy wait up to that much longer than the item's `wakeFrame` before it falls (§ Simulation). Several sources: each copy picks one from the seed.
- **`held`**: a copy put somewhere by a person or `copies.hold` takes exactly that place (the copies item's space, rotate X then Y then Z, uniform size `s`), whatever the layout says; a held copy beyond the count is not drawn.
  (v1.25) **A keyed copy** is a `held` entry with `"anim": {"x"?: [one per frame], "y"?, "z"?, "rx"?, "ry"?, "rz"?}` (Turn into keys on a falling copies item; `copies.key`): each track moves that value frame by frame (frames `start..end`, the length checked like an effector's), and with `anim` every one of `x y z rx ry rz s` may be left out: the layout's value stays (a turn given in part keeps the rest of the layout's turn, as X·Y·Z degrees; no `s`: the layout's size). Keyed copies are written as one time sample per frame of positions and orientations; effectors act on top of them. A copies node with a stored fall (`sim`, § Simulation) ignores the keys of its simulated copies.
- **Effectors** ("Change near"), in order, at each frame: w = falloff(distance(the copy's place in the world, `centre`) / `radius`), `smooth` = smoothstep, `linear`, 0 outside. `scale`: size × max(0, 1 + amount × w) (−1: gone at the centre); `turn`: amount × w degrees round the copy's own `axis`; `push`: amount × w metres away from the centre; `colour`: the copy's colour mixed toward `colour` by amount × w (0..1). Plain values when nothing moves; when an effector's `anim` or the copies item moves, what the effectors change is written as one time sample per frame (no sub-frame samples: copies changed by an effector don't motion-blur).
- **Colour per copy (v1.27):** two primvars on the instancer, interpolation `vertex` (one per copy). `primvars:displayColor` (colour3f) is the copy's colour over 0.5 grey, Storm's own colour for a mesh with no material: **Storm** shows it only on sources with **no material** (UsdPreviewSurface doesn't read it). `primvars:rostrumTint` (colour4f) is the change's own colour and its share 0..1 (each colour effector lays its colour over what is there by amount × falloff). **Cycles** shows it on sources **with a material**: our patched Hydra plug-in (`libs/cycles-rostrum.patch`, `instancer.cpp` / `geometry.inl`, library folder `-r4`) gives each copy the tint as its Object Info colour and alpha, and every material's Cycles graph mixes it over the base colour (`CopyTint` / `CopyInfo` in core/src/materials.cpp; alpha 0 on everything that is no tinted copy, so nothing else changes). Block-view materials and sources with no material show no tint in Final; a copies item while it simulates shows none.
- **Where the copies are (v1.27):** request `copies_box` `{"item", "frame"?}` (the shot's first frame by default) answers `{"lo": [x, y, z], "hi": [x, y, z]}`, world, aligned: every copy as drawn then (laid out, held, keyed, effectors, or where a stored fall has it) with its source's bounds; `lo` / `hi` null when it has no copies. Framing (`shot.frame`) uses it.
- **On a clay (v1.27):** a `surface` that is a clay item is read after the clays are brought to their steps (a clay's surface reaches the stage only then), so the copies are laid out last; `onTop` and the rest as for any surface.
- **Seen test:** when `seenBy` names a camera (the shot's, when the layout is `surface` and the document's `onlySeen` is on), after the stage is built the core draws Storm depth pictures through it (480 wide, `seenSize`'s aspect) with this copies item left out, at the shot's first and last frame and every 12th between (8 at most), and a copy is seen when its base or its bounds' centre is seen (as in `sees`) in any of them. Copies not seen go into `invisibleIds`: neither Storm nor Cycles draws them. The scene reply's `copies` gives the numbers.
- **Fails loudly:** a field out of range (`<id>.<field>`); no source (`<id>.children`); a light, camera or copies as a source; `surface` empty, unknown, inside this copies item, or with no mesh (a clay can't be scattered on yet); `seenBy` not a camera; an effector track of the wrong length.

### Clay (v1.13, Priyam brief CL1; core/src/clay_*)

A clay is a narrow-band distance volume (OpenVDB 13, values in grains, half-width 4) changed only by its steps, in order. Every position is in the clay's own space (metres). Each step:
- piece: `{"key", "kind": "piece", "op": "add"|"carve", "a": [x,y,z], "b": [x,y,z], "radius", "blend", "mirror"}` — a sphere at `a` (or a capsule `a`..`b`), joined (or cut) with a smooth blend of `blend` metres; `mirror` = also at x → −x.
  - (v1.22) `"pairs"` (optional): `[[x, y, z, r, most], …]`, balls (clay space, metres) of earlier pieces this one doesn't touch, each with the most blend it may have toward them. Within `blend` of a ball's surface the blend eases smoothly (smoothstep over that distance) from `most` at the ball up to `blend`; the nearest-reaching ball wins. So a join is decided per pair: soft where the piece touches, never webbing across a gap (rostrum3d/clay_reach.py makes the list). Absent or empty: `blend` everywhere, as before.
  - (v1.15, CL3) `"shape"` (absent = `sphere` / `capsule` as above, from `a`, `b`, `radius`) may name a shape instead, in place of `a`, `b` and `radius`; `op`, `blend`, `mirror` as for a ball, and every shape joins the clay already there with the same smooth blend:
    - `"shape": "outline"` + `"plane": [ox,oy,oz, ux,uy,uz, vx,vy,vz]` (an origin and two unit, perpendicular in-plane axes) + `"outline": [[u, v], …]` (≥ 3 points in the plane, metres, closed last → first; self-crossings allowed, inside = even-odd) + `"puff"` (0.1..3, default 1): a drawn shape puffed out both ways from its plane (along u × v). Every point inside the outline is the centre of a ball as big as its distance to the outline; the shape is all those balls, stretched × `puff` across the plane: at 1 a disc becomes a ball and a strip a round bar, as thick in the middle as the outline is wide there.
    - `"shape": "spin"` + `"plane"` + `"profile": [[r, h], …]` (≥ 2 points, r ≥ 0 the distance from the axis, h the height along it, metres): the profile, closed by the axis (its first and last points joined to it), spun round the axis through the plane's origin along `v` (u points to the profile's side; it doesn't change the shape).
    - `"shape": "item"` + `"source": "<item id>"` (+ `"sourceKey"`, Python's hash of the source, read only for the key): the item's meshes (its prim and every mesh below it, hidden ones too; the shallowest prim of that name under `/World`) at the shot's first frame, moved into the clay's own space through both transforms as they are when the step is applied, turned into clay at the clay's grain (OpenVDB's mesh to level set; a closed mesh gives a closed solid). The made shape is kept for the clay's last 8 drawn / spun / item pieces, so an undo and redo doesn't make it again.
    - Inside the core each is a distance field (core/src/clay_shapes.*): the outline on a 2-D grid of about a grain per cell in its plane (at most 512 a side), the spin as an exact 2-D distance to the profile on such a grid, the item as a level set reaching the band + the blend past the surface. Sphere and capsule pieces are computed exactly as before (the same steps give the same hash).
    - **Fails loudly** (`<clay>.steps[i].<field>`): an unknown `shape`; `plane` not 9 numbers or its axes not unit and perpendicular (within 0.001); fewer than 3 outline or 2 profile points, a point that isn't 2 numbers, a profile r < 0; an outline or profile (with the axis) enclosing no area, or an outline thinner than a grain; `puff` out of range; an item `source` that is empty, not in the scene, or with no mesh with faces (or a mesh with a face naming a missing point).
- stroke: `{"key", "kind": "stroke", "op": "add"|"carve"|"smooth"|"pull"|"flatten"|"crease"|"mask", "radius", "strength", "mirror", "accumulate", "falloff"?, "spacing"?, "frontOnly"?, "invert"?}` plus exactly one path: `"dabs"` (absolute path of a `.dabs` file, `sculpt` § 1), `"dabList"` (inline `[[ax,ay,az, nx,ny,nz, bx,by,bz], …]`, each row optionally followed by `radiusScale, strengthScale`), or `"path": [[x,y,z], …]` + `"dir": [x,y,z]` (an agent's stroke: the path resampled every `spacing` × radius, each dab where a ray along `dir` meets the clay as it is then, starting max(0.08 m, 4 × radius) before the point and reaching as far past it; resolved by the core every time it builds, always the same).
  - (CL2) `falloff` 0..1 (default 0.5): how a dab's effect fades from its centre to its rim; 0 soft (a narrow bell, (1 − t²)⁴), 0.5 the CL1 curve (1 − t²)², 1 hard (full strength out to 0.8 of the radius, then a short edge). Every brush and the Mask use it. `spacing` 0.05..1 (default 0.3): dabs every `spacing` × the radius along the path (an agent's path here; the screen's stroke uses it on screen, `sculpt`). `frontOnly` (default false for a step without it): a dab whose ray lands on a surface facing away from it (the far side of a thin part, reached through it) is skipped. `invert` (default false): Flatten puffs out instead (towards a low dome above the average surface, its top 0.25 × radius × strength up, only ever adding clay), Crease pinches up to a ridge instead of digging a groove, Mask takes the mask away; Add, Carve, Smooth and Pull ignore it (the screen swaps Add ↔ Carve itself).
  - (CL2) Flatten works towards the average surface under the brush (the plane through the falloff-weighted mean of the surface points within the radius, square to their mean normal; the dab's own point and normal when too little surface is under it). Pull moves the clay by the drag since the dab before, along the surface (all of it at strength ≥ 0.5, strength × 2 of it below); a drag longer than one dab can move (2 grains) is cut into up to 4 dabs at the same spot, all stored. A dab's `radius` and `strength` are the step's × the dab's `radiusScale` / `strengthScale` (pen pressure, both 1 without a pen).
  - (CL2) **Mask**: a clay has a mask, 0..1 per grain (0 everywhere at first), kept beside its distances. `mask` dabs paint it towards 1 by strength × falloff (`invert`: towards 0); they change no surface. Every other dab changes a grain by (1 − mask) as much, so fully masked clay doesn't move. Pieces ignore the mask. The mask is part of the clay's state: undo puts it back with the distances, `clay_info.hash` covers it (a clay that never had a mask hashes as in CL1), the cache `.vdb` holds it as a second float grid named `mask`, and live = replay holds for it. (CL2b) The quick view shows it: masked clay is drawn up to 60 % darker (a per-vertex `primvars:rostrumMaskShade` read as each material's occlusion in Storm, and `displayColor` for a clay with no material); Final renders don't show it.

`key` is the step's chain hash (Python makes it; the core only compares keys). After each `scene` the clay store brings each clay to its steps: the same keys, nothing; more steps, only the new ones; fewer, the chunks the last steps replaced are put back (kept for the last 64 steps); anything else: the `cache` file if it is there (and more than 8 steps would be applied), else back to the shared steps and on, else all steps again. Applying many steps (all but the last 64, which keep their undo records), strokes from stored dabs run in parallel where they don't touch: each stroke waits only for the earlier strokes whose chunks it reads (its dabs' reach + 2 chunks) and works on a private copy of them; its chunks are written back one stroke at a time, so the clay is bit for bit the clay of applying them in order (core/src/clay_replay.h). Live strokes and the last 64 steps are applied one by one. After a change the store writes the volume to `cache` on a thread of its own (`.partial`, renamed; the folder made), and deletes the cache file it wrote before for that clay. **Fails loudly:** a missing `.dabs` file, a file that isn't one, a path that isn't absolute, a step with no or two paths, `dir` zero, a `detail` out of range (`<id>.steps[i].<field>`).

**Painted clay (v1.17, Sam brief 3d-cl4; core/src/clay_surface.*).** A clay node may carry `"paint": {"file": "<absolute path>", "size": 64..16384}` beside `props` (Python sends it only when the clay holds paint layers; `file` is its cache path for exactly the clay's last step, `detail` and `size`). After each `scene`, once the clay is at its steps, the core gives its surface an unfolding:
- if `file` holds exactly the clay's surface (magic, version, `size`, and the block list with each block's triangle count) it is read; else the full-detail blocks, as drawn, are welded into one surface (points at exactly the same place are one; the blocks in block order, each block's triangles in its own order), unfolded by xatlas into one `size` picture (faster chart options than `unfold`: charts grow further, pieces on 4-pixel steps), and written to `file` (`.partial`, then renamed; the folder made). A clay with no surface gets a file with none.
- every full-detail block prim gets `primvars:st` (TexCoord2f[], faceVarying, one per triangle corner) from the file, so the clay's paint pictures show in Quick and Final alike. A block changed later (a dab, a step) loses its `st` (the material's own value shows there) until the next `scene` with `paint` puts it back. A clay with no `paint` has no `st`. The stroke's coarse preview blocks never have one.
- `file` is `CLS1`, little-endian: `char[4] "CLS1"`, u32 version (1), u32 size, u32 nPoints, u32 nTris, u32 nBlocks, f32 points[3 × nPoints] (clay space, welded), f32 normals[3 × nPoints], i32 tris[3 × nTris] (into points), f32 uv[6 × nTris] (per triangle corner, 0..1, t up, as `st`), i32 blocks[4 × nBlocks] (x, y, z, triangle count; the triangles are the blocks', in this order).
- The Final look and `render` never show the stroke's coarse preview: a stroke begun after a `view` with renderer `cycles` gets no preview (its dabs work on the clay itself), and a `render` during a stroke drawn on the preview fails (`render: a clay stroke is being drawn …`).
- **Fails loudly** (`<clay>.paint.<field>`): `paint` not an object or with other fields, `file` not an absolute path, `size` not a whole number 64..16384; the file can't be written (`<clay>.paint.file`); xatlas can't lay the surface into one picture (`<clay>.paint`).

**Clay in Cycles: one closed mesh (v1.19, Sam brief CL6; core/src/clay_whole.*).** Cycles' light under the surface (random walk) stays inside one closed mesh only; drawn as its open block prims, a clay let the walk out at every block's edge (see-through, the block borders a dark cross). So each clay also has, beside its blocks, `<clay>/whole` (the blocks with no `st`, welded) and `<clay>/whole_painted` (the blocks with `st`, welded, `primvars:st` faceVarying, the blocks' corners in order), each present only when it has triangles. They are the blocks exactly as written (posed, for a clay with bones), welded where points sit at exactly the same place (the painted clay's weld, § Painted clay), smooth vertex normals, the clay's transform and material (inherited from its Xform). Both are authored `visibility = invisible`: Storm, the stylized look, `pick` and outlines see only the blocks, as before. A Hydra scene-index filter in front of **Cycles alone** shows them with the clay Xform's own visibility and hides every block prim (`clay_<x>_<y>_<z>`, the preview's too) of a clay that has a whole. They are re-welded only right before Cycles draws (each frame of a `render` with renderer `cycles`, after the frame's pose; a `view` with renderer `cycles`) and only for a clay whose blocks were written, emptied, posed or given / lost `st` since; never during a stroke drawn on its coarse preview. A render frame that welded reports `clayWeldMs`. Cost: about one hash insert per block point (an 11 cm head at 1.2 mm grain, ~50 k points: a few ms; a very fine 0.4 mm clay, ~1 M points: tens of ms per changed Final picture), nothing in the Quick view. A flattened export carries the wholes too (invisible).

**Clay with bones (v1.18, Sam brief CL5; core/src/clay_skin.*).** A clay node may carry `"skin": {"rest": [[hx, hy, hz, tx, ty, tz] per bone], "pose": [[move per bone] per frame, start..end]}` beside `props`, exactly as a mesh's (§ 2 Item types, Bones), in the clay's own space (Python sends it for a clay with bones that bends with them).
- Every point of every block (full-detail and the stroke preview's alike) is weighted by the mesh's rule (the 4 nearest bones, 1 / distance⁴ to their rest segments, normalised; core/src/skin.cpp `skin_weights`), with one change for clay (CL5c): a point behind a bone's head (before it along the bone's axis) counts as farther from that bone by 3 × that distance, so a limb whose head sits on the body's surface doesn't drag the body behind it (`ROSTRUM3D_CLAY_SKIN_BEHIND` sets the 3); then pruned: an influence under 2 % of the point's total is dropped and the rest renormalised (clay only; a mesh's skin is unchanged), so a block far from a bone doesn't follow it and isn't re-written when only that bone moves. Zero-area placeholder blocks are never bent and bent by linear blend (points; normals by each move's inverse transpose, blended, unit length). The block prims hold the **posed** points, normals and extent as plain values (not time samples): `view`, `render` and `pick` at frame f first pose every skinned clay with `pose[f − start]` (clamped to the table), or with the last `clay_pose`'s moves until the next `scene`. Only the blocks whose bones moved are re-written; nothing is re-meshed. A clay with no `skin` is drawn exactly as before.
- **Blending (v1.19, CL6):** a clay's points are moved by the **dual-quaternion** blend of their bones' moves (each move a turn and a shift; the blend is one turn round a blended pivot, normalised), so a point shared by the body and a sharply raised arm keeps its distance from the joint instead of being pulled to the average of its two places (the linear blend's pinch). The normal turns with the same blend. When any move of the pose is not a pure turn and shift (a scale), that pose is blended linearly (Σ wᵢ Mᵢ) as before; `ROSTRUM3D_CLAY_SKIN_LINEAR=1` forces the linear blend (to compare). A mesh's `skin` is unchanged (UsdSkel's linear blend).
- **Parts (v1.20, CL7):** a clay's `skin` may also carry `"parts": {"origin": [x, y, z] (the grid's low corner), "cell": metres, "dims": [nx, ny, nz], "cells": [value, count, …] (run-length, x fastest; value = the piece: 0 the body, n a limb; 255 outside), "bone": [piece per bone], "pieces": [{"from": the bone index it hangs from (−1 for the body), "first": its first bone, "blend": metres} per piece]}` (rostrum3d/skin_parts.py, from the joint finder). A point's piece is its cell's (else the nearest inside cell of the 26 round it); each bone's 1 / distance⁴ is then multiplied by 1 for the point's own piece's bones, by a fade (1 within `blend` of the joint, smoothly 0 at 2 × `blend`) for the bone where its piece meets a neighbour (a limb's first bone seen from the body; the body bone a limb hangs from seen from the limb), and by 0 for every other bone. So a raised arm moves its own clay and stretches the shoulder, never the body's side beside it. Without `parts` the rule above is unchanged. A new `skin` with the same `rest` and the same `parts` only takes the new pose table. **Fails loudly** (`<clay>.skin.parts…`): runs that don't cover the grid, a `bone` list not one per bone, a piece number that isn't there.
- Weights are made as each block is written (so a drag's first move weighs nothing); a block re-meshed later is weighed again. A new `skin` with the same `rest` only takes the new pose table; a different `rest` re-weighs every block.
- The clay's steps, cache file, `clay_info.hash` and painted surface (§ Painted clay: unfolded from the **rest** surface, so its `st` never depends on the pose) are those of the rest clay.
- **Sculpting a posed clay** (`sculpt`): the clay is posed for the stroke's `frame`; each pointer ray meets the DRAWN (posed) surface (ray against the posed block triangles the core keeps, blocks culled by their bounds) and is carried into the rest clay through the inverse of the blended bone move at the hit (the same blend as the drawing, its weights barycentric over the triangle's corners), starting 6 grains before the spot, so the volume's own march lands at the same spot of the rest clay; a ray that misses the drawn clay goes through the last hit's move (none yet: no dab). The stored dabs are rest-space dabs (mirror works in rest space: the change shows on both sides in every pose), so live = replay holds. The reply's `point` / `normal` are where the brush is drawn (the dab's rest spot through the same move).
- `save` writes the blocks as last drawn (posed for the last frame shown).
- **Fails loudly** (`<clay>.skin…`): as a mesh's skin (an empty `rest` or `pose`, a frame without one move per bone, a list that isn't 6 / 12 numbers).

## 3. Render

```json
{"render": {"camera": "cam", "renderer": "cycles", "frame": 0,
            "width": 1920, "height": 1080, "samples": 256, "denoise": true,
            "exr": "C:/…/still-{frame}.exr", "png": "C:/…/still-{frame}.png",
            "view": "", "exposure": 0, "timeoutS": 600, "progress": false}}
```

- `frame` or `frames: [first, last]` (inclusive, within the shot).
- `renderer`: `storm` (Hydra's GL renderer, fast), `cycles` (path traced, final; GPU through OptiX when the machine has it, else CPU, named in the reply), `stylized` (our Hydra plug-in, P-3D-3). Any other name is an error listing these.
- **Domes are the same in every renderer (H16).** Storm (and, before v1.23, the stylized renderer) gets the scene's dome exactly as the live viewport does (seen behind the scene and lighting it, `core/src/sky.cpp`), so a Storm render equals the quick view. Cycles' Hydra plug-in reads a dome's picture with +Z up (Blender's way) where USD and Storm use +Y up; a Hydra filter in front of Cycles alone turns every dome to match (`core/src/dome_cycles.*`), so the horizon and the sun sit in the same place in both. Storm limits that remain: no reflections of other objects (a mirror ball shows only the sky), no shadows or contact darkening from the dome's sky. The small bright sun of an HDR is taken out of Storm's dome and drawn as a distant light with a shadow map (H17, § 4 `sun`), so it lights and shades like Cycles' sun, with a harder shadow edge.
- `stylized` (v1.23, renderer `stylized` only; anything else in it, or with another renderer, fails listing what is accepted): `{"supersample": 1..4}`, default 2: the stylized renderer draws at that many times the picture's size and scales down (renderer setting `rostrum:ss`; the viewport uses 1). Its shadow maps are 2048 square (`rostrum:shadow:size`) in both, so preview ≡ export apart from the supersampling.
- `samples`, `denoise`: Cycles only (others ignore them). A progressive renderer is rendered until it says it is done; past `timeoutS` the render fails (never a half-finished picture with success).
- **Outputs:** `exr` = scene-linear half-float RGBA OpenEXR (for the Editor); `png` = 8-bit sRGB picture through **OpenColorIO**: the config's scene-linear space to the display `sRGB`-type display and `view` (`""` = the config's default view), after `exposure` stops. At least one of `exr` / `png`. `{frame}` is replaced by the frame number (4 digits); a range needs it. The config is the one named by `OCIO`, else OpenColorIO's built-in CG config. Each file is written to `<name>.partial` and renamed when whole.
- **`passes`** (v1.12, Cycles and `exr` only; `core/src/passes.*`): a list of `light`, `shadow`, `reflections`, `masks`, `depth`, `normal`, each written as named channels of the same EXR after `R G B A` (the beauty): `light.R/G/B` (light on matte surfaces: Cycles' diffuse, direct + bounced, surface colour included), `reflections.R/G/B` (Cycles' glossy), with either of them `rest.R/G/B` (transmission + emission + background + volume), so **light + reflections + rest = the beauty before noise clean-up** (exactly with `denoise` off); `shadow.A` (0 lit .. 1 in full shadow: 1 − the matte surfaces' direct light ÷ the same with no shadows; the frame is rendered a second time with Hydra's `rostrum:castShadows` off, so it takes twice as long); `masks.<item id>` (one per item of the scene, groups included, cameras and lights not: 1 where the item or anything it holds is seen, else 0; from Cycles' object ids, first sample only, so hard-edged); `depth.Z` (32-bit, distance from the camera plane in metres, 0 where nothing is); `normal.X/Y/Z` (surface direction, world space, Y up). Half-float except depth. The reply's `channels` lists the file's channel names in order (`[]` with no `exr`). Needs the patched Hydra plug-in (`-r3`, `libs/PATCHES.md`), which maps the outputs `diffuse`, `glossy`, `transmission`, `volume`, `emission`, `background`, `diffuseDirect` to Cycles' passes.
  (v1.30, PR9; library folder `-r5`) three more: **`lightGroups`**: `lightgroup_<light>.R/G/B`, one per light of the stage (named as its prim; a dome too), that light's own share of the picture as seen (Cycles' light groups, direct + bounced), so the groups add up to the beauty before noise clean-up less what glows on its own (emissive surfaces, which belong to no group); not cleaned of noise. **`cryptomatte`**: `CryptoObject00`, `01`, `02` `.R/G/B/A` (32-bit), Cryptomatte 1.2 object ranks (per pixel the 6 items covering it most, as `id, share` pairs, sorted), one id per top-level item (`/World/<item>` with all it holds, the parts' shares added), the id MurmurHash3_32 of the item's id as a float; the file's header carries `cryptomatte/<key>/name` (`CryptoObject`), `hash` (`MurmurHash3_32`), `conversion` (`uint32_to_float32`) and `manifest` (JSON, item id -> 8 hex digits), `<key>` the first 7 hex digits of the name's hash: what Nuke, Resolve/Fusion and Natron read. **`motion`**: `motion.X/Y/Z/W` (32-bit), motion vectors in pixels, x right, y up: X Y = where the point was a frame before minus where it is, Z W = where it is minus where it will be a frame after (Blender's Vector pass). Cycles makes vectors only with its motion blur off, so **with `motion` the picture renders sharp** (the shot's shutter is not used; the Editor blurs from the vectors) and every move, the camera's too, is sampled a frame either side (`rostrum:shutterOpen` -1, `Close` +1).
- The picture is `width × height`; the camera's sensor height follows that aspect.
- Timings are per frame and in total; video memory is this process's peak (Windows DXGI) plus the whole card's use (NVML), so the agent sees what fits on a 4 GB card.

## 4. The live viewport (`view`, H13)

```json
{"view": {"camera": "cam",                                        // look through a scene camera, OR a free camera:
          "eye": [0.3, 0.2, 0.5], "target": [0, 0, 0], "fov": 30,  // fov = vertical, degrees; up is +Y
          "frame": 12, "width": 960, "height": 540,
          "renderer": "storm", "exposure": 0, "studio": 1.0, "sceneLights": true,
          "selected": ["device"], "view": "", "ao": 1.0, "aoRadius": 0.3, "dof": true,
          "ghosts": [{"frame": 8, "items": ["lid"], "tint": [0.85, 0.22, 0.18], "opacity": 0.4}]}}
```

- Give **either** `camera` **or** `eye` + `target` + `fov` (the free camera orbits around `target`). Near/far for the free camera follow its distance.
- `renderer`: `storm` (default), `stylized`, or `cycles` (the Final look, below). **Stylized and lights (v1.23):** the stylized renderer reads the scene's own lights, domes included, as the UsdLux lights they are (real brightness, § Materials, How lit); it is never handed the scene's dome again as a viewport light (that lit twice). With no scene dome lighting (none, or `sceneLights` off) it gets the studio as a dome viewport light, and the renderer setting `rostrum:studio:level` = what a white floor shows under the studio (Rec.709 luminance; 0 when the studio doesn't light), since a viewport light carries only the picture. The viewport sets `rostrum:ss` = 1 and `rostrum:shadow:size` = 2048.
- **Final look (v1.5)**: with `renderer: "cycles"` each `view` request does one step of progressive Cycles and returns at once with the picture as far as it has got; sending the same request again carries on, and any change (scene, camera, frame, size, settings) starts it over. `samples` (1..65536, default 128) and `denoise` (default true) belong to it; given with any other renderer they are an error. Through a scene `camera` it takes the camera's own path exactly as `render` does (same lens, depth of field from Cycles itself), so it matches the Render button; a free camera works too. The viewport-only extras are off: no contact shading (`ao`), no viewport depth-of-field blur, no selection outline, no studio light (the scene's own lights light it). `exposure` and `view` still apply as sent. The reply's `final` and `vram` fields are listed in § 1. The process keeps its Cycles engine until it ends: to give the graphics memory back, the screen ends the viewport's engine process on leaving Final (`Engine.release()`; a fresh one draws Quick), because ending one Hydra Cycles engine inside a running process crashed it.
- `exposure` (stops) and `view` (OCIO view) as in `render`; the picture goes through OpenColorIO like the PNG does, on the graphics card (H20, core/src/view_post.* and ocio_gpu.*: the same config, display and view as the PNGs, as a shader; measured within 1/255 of the CPU path).
- `ao` (H20): contact shading (screen-space ambient occlusion, from Storm's depth) strength 0..2, default 1; `0` = off. `aoRadius`: how far it reaches, in scene units (default 0.3). Viewport-only, because Storm has no ambient occlusion of its own: without it a ball on a floor under an even sky reads flat. It darkens what the camera sees of corners and contacts; what is hidden on screen (the floor under a ball) can't darken anything.
- `dof` (H20, default true): depth of field when looking through a scene `camera` whose depth of field is on (its f-stop, focus distance, focal length and sensor width; thin-lens blur, matching Cycles' blur behind the focus). A blurred object in front of the focus doesn't spread over the sharp things around it, unlike Cycles. The reply's `cameraDof` says whether the camera looked through has depth of field on (the screen shows its Depth of field switch only then). The reply's `notInQuickView` (v1.3) lists the scene's product-lighting settings Storm can't show (a light's `spread`, its `lightsOnly`), one line per light, `[]` when none.
- `studio`: strength of the viewport's studio environment (a soft studio dome made by the core, so metal and glass have something to reflect); `0` = off. `sceneLights`: the scene's own lights on or off. Both are viewport-only: renders never see them. The studio is never seen by the camera. When the scene has its own dome light and `sceneLights` is on, that dome lights the viewport instead of the studio and is seen behind the scene, as in Cycles (core/src/sky.cpp: Storm is handed the dome's picture, or a flat one, × colour × intensity × 2^exposure (× its colour temperature), because Storm reads only a dome's picture; Cycles gets the same picture; Storm draws into its own colour picture so its sky pass runs). The reply's `sceneDome` (true / false) says whether the scene's dome lit this picture, i.e. the studio was not used (the screen hides its Studio light slider then). In Storm, a dome picture whose light sits mostly in one small bright patch (a sun) is split once per picture (core/src/dome_sun.cpp, cached as `%USERPROFILE%\.rostrum\cache\3d\domesun-v1-*`): the patch is painted over with the sky around it, and Storm gets, beside that picture, a distant light with a shadow carrying exactly the light taken out (core/src/storm_sun.cpp), so the total light is unchanged; Cycles and the stylized renderer keep the whole dome. The reply's `sun` is then `{"toward": [x, y, z] (world direction towards the sun), "share": 0..1 (its part of the dome's light), "angleDeg": its apparent size}`, else `null`. A Storm `render` gets the same sun.
- `selected`: item ids drawn with an outline (a 2-pixel ring in the kit's accent colour).
- `hovered` (v1.16, 3d-v4; optional): item ids drawn with the thin hover outline: 1 pixel, the accent laid at 60 % over the picture, so it reads lighter and softer than the selection ring, which wins where both meet. Drawn from a mask of its own (the hovered items alone, unlit, as the selection's). The screen sends it only while there is something hovered (Draw / Spin armed: the clay a drag from the pointer would join), so an older core never sees it. An unknown item is an error naming `view.hovered`.
- `ghosts` (v1.9, onion skin, brief 17; core/src/ghosts.*): at most 8, each `{"frame"` (a frame of the shot), `"items"` (one or more item ids), `"tint"` ([r, g, b] linear, each 0..1, default white), `"opacity"` (0..1, default 0.35)`}`. Each ghost's items are drawn alone at its frame, lit like the picture, into a picture of their own; it is laid over the scene see-through in its tint (its own light and shade kept as brightness), in the order given, before depth of field, the colour transform and the selection ring. No depth test: a ghost shows over what stands in front of it. A frame outside the shot, an unknown item, an empty `items`, a tint or opacity out of range, or an unknown field is an error naming `view.ghosts[i].<field>`. **Quick look only:** with `renderer: "cycles"` (Final) `ghosts` is an error; renders never take it. The screen sends ghosts only while onion skin is on (an older core refuses the unknown argument loudly).
- The pixels (straight-alpha RGBA8, top row first, background laid in; read straight from the graphics card into the slot) are written into a named shared-memory block with two slots used in turn, as in Rostrum2D's `pixels` (`Local\rostrum3d-<pid>-<n>`; Python: `mmap.mmap(-1, size, tagname=name, access=mmap.ACCESS_READ)`). The reader must be done with a slot before it asks for the view after next. Windows only for now.
- **`pick`** takes the same camera choice: `camera`, or `eye` + `target` + `fov`.
- **In the window (v1.14, 3d-v1):** the screen's live view is the same core inside the app's own window (the
  `Rostrum3DView` QML module, core/view/viewport_item.*; Python side app/screen3d/view_item.py), answering the same
  request lines through the same handler (core/src/serve.h `answer`) on Qt Quick's render thread. Its `view` pictures
  are drawn straight into the view's texture (same view post, pixel-identical to the engine's pictures), so its reply
  has no `shm`; replies there add `frame`, `tRender0` and `tRender1` (steady-clock ms: the frame that drew it). Pictures
  for checks (offscreen windows), the Final look, `render`, `geometry`, `unfold`, `save`, `inspect_usd` and everything
  agents and MCP ask stay with the engine program, which loads the same scene JSON.


**Imports of other formats (v1.20, Hem brief 29; core/src/convert*.cpp, convert.h).** An `import` whose `file` is a glTF /
GLB (cgltf), OBJ (tinyobjloader, with its .mtl), FBX (ufbx, binary or ASCII) or Alembic (Ogawa) file is turned once per
session into an in-memory USD layer (converted again when the file's size or time changes) and referenced like a USD
file; the file is never rewritten. The layer: a default prim named after the file holding the file's node tree as Xforms
and Meshes (points, polygons, normals, `st`), its materials as UsdPreviewSurface under `<default>/Materials` (colour,
metallic, roughness, emission, opacity, a base-colour picture; pictures stored inside a file are written once to
`%LOCALAPPDATA%\Rostrum\3d-import-cache\`), upAxis Y (Z-up sources turned upright), `metersPerUnit` the file's own
unit (geometry never rescaled: the Python side scales the import, `import.add`), and an Alembic file's animation (moving
transforms, moving points) as time samples, one time code per source frame at the file's own rate (USD maps it onto the
shot's frames). (v1.27) A glTF file's first animation plays: the moved nodes' transforms and each skinned mesh's points and normals (skinned in the core from JOINTS_0 / WEIGHTS_0, so Storm and Cycles draw the same) as time samples at 30 a second (convert_gltf_anim.h); morph targets and other animations are not read. An FBX file's first animation stack plays the same way: ufbx evaluates the whole scene per sample (its transform chain and curves), the animated nodes' transforms and each skinned or blend-shaped mesh's points (a skin's normals too) as time samples at 30 a second (convert_fbx_anim.h); other stacks, constraints and vertex caches are not read. (v1.27) `save` without `flatten` writes each such in-memory layer beside the file, `<file name>_imports/<name>-<16 hex>.usdc` (named by the source file's path, size and time: written once), and references it there by a relative path, so the saved file opens on its own. **Fails loudly:** an unknown extension; a
file its reader can't read (`<id>.file: could not read model.fbx: <the reader's reason>`); a file with nothing to import.

## Texels (v1.22, Hem brief 21; core/src/texels*.cpp, Hydra::ids)

`file` is raw little-endian float32, rows top first, `width` columns, **4 floats a pixel: u, v, item, distance**.

- `u`, `v`: the surface's `st` where the pixel's centre ray meets it (as `pick`'s `uv`: canvas pixel x = u × size,
  y = (1 − v) × size); NaN where the prim drawn there has no `st` (or nothing is drawn).
- `item`: index into the reply's `items`, −1 where nothing is drawn or what is drawn is no document item. A copy
  (§ Copies, point instancer) is its copies item, with u v NaN.
- `distance`: metres from the camera's eye to the surface seen, −1 where nothing is drawn.

How: one Storm picture through the camera (the selection mask's engine: no sky, unlit) gives each pixel's prim id
and depth (Storm's own depth output); the copies' `sees` and seen test draw through the same function. The id picture
is drawn without the scene's materials, because Storm's glass pass overwrites every pixel's prim id: glass is seen as
its front surface (the front of the vase, not what is behind it). Storm writes no `st` or face outputs, so for
each mesh prim seen the core meets every one of its pixels' rays with the mesh's triangles (each triangle tests only
the pixels it covers on screen; the face nearest the depth Storm drew wins) and blends the `st` of that face's
corners (face-varying or per point), as `pick` does for one ray. A painted clay's blocks carry the clay's unfolding,
so its pixels get u v. An instance of a native USD instance or a point instancer inside an import gets u v NaN (its
own transform isn't known from the prim id). A skinned clay is seen as drawn at `frame`. Python:
`rostrum3d.texels` (`read`, `Picture`, `geometry_key`, `cached`), `Engine.texels`.

## Simulation (v1.24, Sam brief 25; core/src/sim*.cpp, Jolt Physics 5.6.0)

`{"simulate": {"start", "end", "fps", "folder", "progress"?, "ground": {"y"} | null, "bodies": [{"item", "kind": "falls" | "still",
"mass" (kg, 0 = from its size as solid plastic, 1100 kg/m³), "bounce", "friction", "starts": "moving" | "asleep", "shape": "exact" |
"box" | "sphere", "velocity"?: [vx, vy, vz], "wakeFrame"?: n}, …]}}` runs rigid bodies on the **held stage** (send the scene without a stored
result first: the start poses are read at `start`). A body is a top-level item (all its visible meshes, one body) or a
`copies` item (every copy is a body; a copies item that itself moves can't fall). `exact` is the convex hull for a falling
body and the exact triangles for a still one; `box` / `sphere` wrap the points. One thread and Jolt's cross-platform
determinism: the same request always gives the same file. With `progress` a line `{"progress": i, "of": n, "frame": f}`
comes after each frame.

`wakeFrame` (v1.28, Falls from; sent only when above 0): a falling body is held still (kinematic: others land on it and bounce
off it) for its first n frames after `start`, then falls with its `velocity`. On a `copies` body each copy waits n plus its
own delay from the item's `varyStart` (§ Copies › Vary), capped at the shot's length. (v1.29) A pour (layout `pour`) adds each
copy's place in the stream (copy *i* of *n* waits `pourTime` × i / (n − 1) more) and gives it a start speed: `pourSpeed` m/s
along the copies item's own −Y, within `pourSpread` degrees of it (from the seed), turned to the world, added to its
`velocity`. In a **stream** (`varyStart` > 0, or a pour with `pourTime` > 0) a waiting copy is not in the world at all until
its frame (it collides with nothing, then appears where it was laid out and falls); its rows hold its start pose until then
and its reply row carries `"appear"`: the shot frame it appears.

Reply: `{"ok": true, "jolt": "5.6.0", "sim": 5, "frames": [start, end], "rows": n, "file": "<folder>/bodies.bin", "bodies":
[{"item", "copy" (-1 for a plain item), "row"}, …], "cloth": [{"item", "file", "points", "triangles", "refined"}, …],
"atRest", "ms", "frameMs"}` (`frameMs`: the engine's time per frame of the shot, bodies and cloth together). `bodies.bin`: float32 little-endian,
frames × rows × [x y z qx qy qz qw], one row per falling body: a plain item's translate and turn (world = its own, it is
top-level; its scale is kept), a copy's position and orientation in its copies item's space. `info` gives `jolt` and `sim`
(the version of this behaviour: part of the stored result's key).

A failure stops the run: `{"ok": false, "error": "bud_copies copy 7 starts inside bowl at frame 0: move it up 4 mm or set
Starts: Asleep until hit", "item", "copy", "frame", "fix"}`; also a body that flies away (over 200 m/s or 1 km) and one
that falls past everything (nothing under it).

**Reading a stored result.** A plain item gets its poses as ordinary `anim` x y z rx ry rz (the Python side). A `copies`
node may carry `"sim": {"file", "row", "rows", "of", "start", "end", "step": 1..3, "smooth": 1..100, "appear"?: [frame per row]}`: copy *c* < `rows`
takes row `row + c` of each frame (frames outside `start..end` hold the ends; `step` holds each pose 2 or 3 frames from
the shot's start, On 2s / On 3s; `smooth` keeps every nth pose and blends between, Simplify). The copies' sizes stay as
laid out; effectors don't move simulated copies. (v1.29) With `appear`, copy *c* is hidden before frame `appear[c]` (scaled to 1e-4 at its
start point, one `scales` sample per frame: the instance count never changes, which Cycles needs), and framing (`copies_box`) and the pick leave it out then. (v1.25) The pick of a copy (`pick`'s `copy`) and the seen test use the copies as drawn: a
simulated copy where it fell at that frame (its `place` in the pick reply stays the laid-out one, what a gizmo starts from);
a simulation's start poses stay the laid-out ones (with keyed copies at `start`).

**Cloth (v1.25, Sam brief 26b).** A body `{"item", "kind": "cloth", "weight" (kg per m², above 0), "stiffness" (0..1),
"pinned": "none" | "top" | "bottom" | "left" | "right" | "front" | "back", "friction", "wakeFrame"?: n}` is a top-level `mesh` item draped as a
Jolt soft body: one particle per point (a third of each of its triangles' weight × area), edge, shear and dihedral-bend
constraints from its triangles (`CreateConstraints`), 8 solver sub-steps per physics step. With `wakeFrame` n (v1.28) every point is held (inverse mass 0, like a pinned point) for its first n frames, so it keeps its first shape and falling bodies land on it; then each point gets its weight back (pinned ones stay held) and it falls from rest. Stiffness sets the constraints'
give against the cloth's own mean point weight: stretch from a little (0) to none (1), bending (× edge length²) from silk
(0) through cotton (0.3, hangs in folds) to card (1). A still body whose Exact surface is closed and convex (its hull holds
no more than 1% over it) collides as that hull, sharp-cornered; any other still Exact body as its triangles. `pinned`: the points within 1% of that side of its world bounds at `start` (Top = highest y, Right
= highest x, Front = highest z) weigh nothing and stay (with long-range attachments so it hangs without stretching); a
side the cloth is flat along (Top on a sheet lying flat) is a failure. Its mesh is refined first: one four-point face (a
plane) becomes a 64 × 64 grid (4225 points, 8192 triangles, diagonals alternating), anything else has every triangle split
in four until no edge is longer than 1/64 of its size (at most 20000 triangles); faces with no area and unused points are
dropped; u v follow (a seam keeps one side's). It lands on still and falling bodies and the ground and pushes falling
bodies; cloths don't collide with each other or themselves (Jolt). Its points keep half its median edge (at least 2 mm)
off what they touch. Failures: it
**tore apart** (an edge stretched past 4 times its length), **flew apart** (a point over 200 m/s or 1 km away), **fell past
everything**; each `{"item", "copy": -1, "frame", "fix"}`.

`<folder>/cloth_<item>.bin`, little-endian: `"RCL1"`, int32 points, triangles, frames (`end - start + 1`), start; int32 × 3
× triangles; float32 × 2 × points (u v); float32 × 3 × points per frame: each point in the item's **own space as it stood
at `start`** (its translate, turn and scale at `start` taken out).

**Reading a stored cloth.** A `mesh` node may carry `"cloth": {"file", "start", "end", "step": 1..3, "smooth": 1..100}`: its
faces become the file's triangles, its `st` the file's u v (face-varying), and its points, normals and extent one time
sample per frame of the shot (`step` / `smooth` as a copies node's `sim`: On 2s / On 3s from the shot's start, Simplify's
every nth frame with straight lines between; frames outside `start..end` hold the ends). It is double-sided; its `skin`,
outline parts and `faceMaterials` don't apply (the item's `material` does). The Python side holds its place (x … sz) at
the shot's first frame, so the stored points sit where they were simulated. A file that is missing or doesn't match its
header is an error naming `<id>.cloth.file`.
