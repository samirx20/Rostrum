# P-3D-2 · Painterly still through USD + Hydra + Cycles

**Question:** through the same USD + Hydra + Cycles pipeline as P-3D-1, can a still of our own reach Arcane / Pinkman.TV quality in that kind of style: hand-painted textures under real light, a painted background, grain?

**Verdict: pass with conditions.** The pipeline does everything this style needs from it: painted textures through UVs, bump and roughness maps, colour management through OpenColorIO, a painted background card, and even light-driven colour ramps with real cast shadows, all through Hydra into Cycles on this laptop in 15–40 s per 1080p frame. The still itself is our own and clearly hand-painted, but it does **not** yet reach Arcane / Mielgo quality: the real-light version reads as painted props in a CG render, and the light-ramp version reads as painted but flat and cut-out. The gap is shading and painting tools (P-3D-3 and P-PAINT), not render power. Judged in detail below.

## What we made

Our own still life (not taken from any reference): an enamel jug, an earthenware bowl with pears, one pear lying on the table, a folded linen cloth on a wooden table, in late-afternoon sun through a window off-frame left, in front of a painted background card of the room. All geometry is generated by `scene/make_scene.py` (lathes, a tube, a draped cloth, a slab, all with UVs). **Every texture was painted by agents** with a small brush engine (`paint/brush.py`), stroke by stroke, looking at the result as they went. No photo textures and no CC0 textures were used.

## Steps

1. Cycles build: as in `proofs/3d-product/README.md` (this proof reuses that build unchanged).
2. Textures: `uv run --with numpy --with pillow python -I paint/scripts/paint_<name>.py` (each writes `paint/textures/<name>.png` and its stroke log `<name>.json`, which replays to the same image with `Canvas.replay`).
3. Look loop (stage, render through the gpu lock, OCIO view): `pwsh -File look.ps1 <out-dir> <name> [samples] [width] [height] [-Ramp] [-Partial] [-Grain 0.035]`.
   - `-Ramp`: the key-light colour-ramp version. `-Partial`: textures not painted yet show a labelled UV checker.
4. UV guides for painters: `uv run --with pillow python -I scene/guides.py paint/guides`.

## Package A · pipeline pieces: what works through Hydra → Cycles

| Piece | Result | How / note |
|---|---|---|
| UVs (`primvars:st`, `texCoord2f[]`) | **Works** | Hydra marks texture-coordinate primvars as Cycles' UV; an unconnected `image_texture` uses them. Checked with a labelled checker render. |
| Image textures | **Works** | Native Cycles node in USD: `info:id = "cycles_image_texture"`, `asset inputs:filename`, `inputs:colorspace`. (`UsdUVTexture` is also translated.) |
| Roughness map | **Works** | second image node, colour space `Raw`, into `principled_bsdf.roughness`. |
| Bump / height map | **Works** | `cycles_bump` fed by a `Raw` height image; checked against a render without it. |
| Tangent-space normal map | **Does not work** | the delegate builds no tangents, so `cycles_normal_map` (tangent space) is silently ignored (pixel-identical render). `materials.py` now refuses `_normal.png` loudly. Fix for Rostrum3D: compute MikkTSpace tangents when the delegate syncs a mesh (a small patch), or use object-space maps. |
| Colour management | **Works** | `render.ps1` sets `OCIO=ocio://cg-config-latest` (the ASWF CG config built into OpenColorIO, BSD-3: nothing to download, no Blender config). Cycles then renders in ACEScg; textures are converted from `sRGB Encoded Rec.709 (sRGB)`. `view.py` applies the view with PyOpenColorIO: `sRGB - Display` / `ACES 2.0 - SDR 100 nits (Rec.709)`. The standalone app still writes the EXR without a view (its own TODO), so the view is our step. |
| Light-driven colour ramps | **Works without OSL** | Cycles has a `raycast` shader node. Graph: `lit = max(N·L, 0) × (1 − raycast(P + 0.05·N, L).is_hit)` → `rgb_ramp` (constant steps) → × albedo → emission. Real cast shadows (window pool, bowl shadow) drive the painted ramp. OSL stays off. Limits: one light direction typed into the material (a sun), no ramps for area/bounce light, no indirect light in the ramp. |
| Painted background card | **Works** | camera-facing quad computed from the camera (fills the frame + 6 %), emission shader, so it shows as painted and is not lit. |
| Sun light | **Works, with a flag** | a UsdLux `DistantLight` with `angle > 0` must set `inputs:normalize = true` in this delegate, or it is ~3000× too dim (its strength is treated as radiance over the tiny sun disk). |

Two traps found on the way, both silent (no error): (1) `raycast.direction` is a *normal*-type socket, and Cycles feeds any unconnected normal socket with the surface normal, so a typed-in direction is ignored; it must come through a node (`vector_math normalize`). (2) A shader-graph mistake (wrong output name) makes the delegate drop the material and render default grey. `render.ps1` now fails when the delegate prints any shader warning, and when the stage file is missing (H1's `render.ps1` rendered an empty scene with success).

First use of the `raycast` node costs a one-time OptiX kernel compile: **168 s and 3 GB RAM**; afterwards the ramp scene renders as fast as the plain one (4 s at 960×540, 64 samples).

### How it was painted

Three member agents (Opus) did the painting work:
- **The brush member** wrote the brush engine, `paint/brush.py`. It stamps procedurally textured tips (round, bristle, flat, chalk); pressure sets width and opacity. It also has colour drift, wet pick-up, paper grain, multiply glazes, polygon masks, and a JSON stroke log that replays exactly. The same member wrote the seeing tools, `paint/look.py`: zoom with a pixel grid, UV-guide overlay, side by side and colour pick.
- **Two painters** then painted the props and the setting, two rounds each. They worked from flat images, UV guides (`scene/guides.py`) and a labelled-checker render as their "where" tool.

After round 1 the lead rendered the frame and sent it back. At frame size most of the brushwork had melted, so round 2 used fewer, bigger, higher-contrast strokes. The jump from round 1 to round 2 is the clearest gain in the proof. The table's colour, height and roughness maps come from one shared stroke list. The props' and cloth's height maps are derived from their paint (`paint/maps.py height`).

### Judged against the quality bar (Arcane; The Witness, Jibaro)

What holds up:
- The textures are genuinely painted by agents, stroke by stroke, and read as brushwork at frame size: the jug's warm/cool strokes and chipped cobalt rim, the bowl's throwing rings and glaze drips, the planks' value steps.
- The light is real and can be directed: a warm pool of sun through a window off-frame, long shadows, cool room light. The painted background card, with its own window of sun, ties into it.
- The light-ramp version is closest in style to the reference: graphic shapes of light and shadow over painted colour, with the bowl's shadow as a painted shape on the cloth.

What does not reach the bar:
1. **Real-light version:** the bump from the paint makes the jug look like textured plaster, and soft path-traced shading smooths the painted look back into CG. Arcane's painted look comes from shading and paint working together (painted light edges, controlled shadow edges), not from textures alone.
2. **Ramp version:** flat and cut-out. The ramp edges are hard, computer-clean lines. Only the sun is ramped (no bounce, fill or rim light), and the edge between light and shadow lacks the painted, broken edge the reference has.
3. **Form and drawing:** the lathe props are simple. The pears read partly as striped melons, because the texture's bands converge at the poles. No ink or line work defines the shapes.
4. **The tools limit the painting quality, not the effort:** the painters worked without seeing the 3D frame (see their list below). Round 2 fixed the stroke scale only because the lead fed renders back by hand.

**Pass with conditions:** USD + Hydra + Cycles carries a hand-painted look correctly, and fast enough on this laptop; Cycles alone can even do one-light colour ramps. Reaching Arcane / Mielgo needs P-3D-3's stylized shading (ramps for every light, painted edges, ink lines) and P-PAINT's "see it on the model" painting tools. Judge again once those exist.

## What the painters needed (first taste of agent painting tools; feeds P-PAINT)

From the three painter agents' own notes, merged:

1. **See the texture on the model in the camera's frame** after every change, even without real light. Flat textures mislead about stroke size: the bowl is squashed ~4× on screen, the jug stretched sideways. A cheap camera view with the texture applied (raster, no Cycles) is the single biggest need.
2. **"Where" both ways:** texture pixel → point in the frame, and frame point → texture pixel, to place chips, blush and wear exactly where the camera looks. (The labelled-checker render was the stand-in.)
3. **A screen-size view:** the texture resampled to how big it really appears, to judge whether brushwork survives.
4. **A lighting preview** (sun + cool fill), because glossy enamel and dark wood hide small colour steps.
5. **One stroke into several maps** (colour + roughness + height together), so maps line up; today each map is painted separately and drifts.
6. **Tiling:** a repeat view and wrap-around strokes, and painting across a lathe's u = 0/1 seam.
7. **Brush-engine gaps:** square-ended block-in strokes (tapered ones make leaf/flame shapes); hue drift as its own setting (colour variation also shifted hue ±20°); soft gradients / value areas; a crisp thin-line tip; stroke recipes for drips, speckles, chips; faster repaints (≈ 50 s per 2048² repaint slows every round).
8. **Value and colour checks** against the other textures: greyscale view, picked-colour swatch, side by side.

## What P-3D-3 (our own stylized Hydra plug-in) must add that Cycles can't

- **Light ramps for every light, including bounce and area light.** The raycast ramp here works for one sun typed into each material; it can't ramp the fill, the bounce or indirect light, and the ramp must be set per material. A stylized delegate should shade by "how lit" per light from the renderer's own light loop, with ramps that are data on the light or material.
- **Ink lines** with width, taper and wobble: silhouettes, creases, contact lines. Cycles has nothing for this (only a wireframe node).
- **Brush-stroke shading:** light and shadow edges broken into painted strokes in screen space, so the frame reads as painted even where the texture is out of focus or tiny. In this proof the brushwork lives only in the textures, and at frame size much of it melts.
- **Per-shot shape bending** (squash, lean, exaggerated silhouettes toward the camera), which a path tracer renders literally.
- **Painted-card compositing that respects the view transform:** the emissive background card goes through the same ACES 2.0 view as the lit scene, so the painting shifts in value and saturation. A stylized pipeline needs a way to show a matte painting as painted (or a view that leaves it alone).
- **Fast look loop:** Cycles' 4–26 s per look is fine for a still but slow for painting feedback; a raster delegate gives the painter's "see it on the model" view in real time.
- From this proof's findings, small fixes to carry into Rostrum3D's Cycles delegate either way: MikkTSpace tangents for normal maps; per-ray visibility (camera / shadow) for cards and blockers; the sun `normalize` default; the OIIO output driver applying the OCIO view.
